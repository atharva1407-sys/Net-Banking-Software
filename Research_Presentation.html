Step 1: Identify the Research Gap 🔍

Literature Survey & Empirical Research Gaps

Systematic analysis of 25+ papers (2021–2025) from IEEE Xplore, ACM DL, and Springer LNCS

Gap 1: Destructive Single-Entry

State Mutation
  • Existing tutorial architectures rely on destructive in-place scalar updates (UPDATE account SET balance = balance - x).
  • Lack of historical state: If connection is severed, system cannot determine why, when, or through which channel funds were altered.
  • Violates ISO 20022 and statutory financial compliance for non-repudiable transaction trails.

Gap 2: Replay Inadequacy

Network Volatility
  • Mobile and flaky 4G/5G connections cause frequent HTTP timeouts, prompting users to re-submit payments.
  • 68% of surveyed open-source systems lack cryptographic idempotency key deduplication.
  • Leads to catastrophic duplicate disbursements and customer overdraft vulnerabilities.

Gap 3: ACID vs Scale Conflict

Concurrency Model
  • Microservice implementations often prematurely adopt eventual consistency / Saga, leading to temporary dirty reads.
  • In retail banking, dirty reads enable immediate double-spending before compensating sagas trigger.
  • Need for bounded READ_COMMITTED isolation + balanced debit/credit journal pairs.

Research Questions & Novel Architectural Contributions

Formulating scientific hypotheses and novel engineering solutions for Web Banking

Focused Research Questions (RQs)

Hypotheses
  • RQ1 (Transactional Invariants): Can an in-line double-entry state machine maintain 100% debit-credit mathematical balance across peak concurrency spikes without distributed lock exhaustion?
  • RQ2 (Idempotency Efficacy): To what extent does a client-keyed unique constraint eliminate duplicate financial execution during simulated 15% network packet loss?
  • RQ3 (Tenant Boundary Defense): Does customer-context security identity injection eliminate Insecure Direct Object References (IDOR) with sub-millisecond query overhead?

Our Novel Architectural Contributions

Core Innovations
  • 1. Idempotent Double-Entry Ledger Pipeline (IDLP): Every transfer concurrently generates paired immutable DEBIT and CREDIT journal entries with balance-after snapshots.
  • 2. Zero-IDOR Customer Scoped Authorization: Enforces findByIdAndCustomerId() ownership directly from the authenticated Spring Security 6 JWT context.
  • 3. Reactive Signal Synchrony: Angular 22 Signals decoupling UI state from polling while guaranteeing zero memory leaks during live ledger updates.
  • 4. Zero-Friction Reproducibility: Integrated dual-profile pipeline (Postgres-compatible H2 dev + Flyway PostgreSQL prod).

Methodology & System Architecture

Double-Entry Financial State Machine

End-to-end request propagation, isolation boundaries, and relational schema

1. Client Tier (Angular 22)

Reactive UI
  • Standalone Component Model: Eliminates legacy NgModules for rapid tree-shakeable loading.
  • JWT Interceptor: Intercepts outbound requests and attaches authenticated Bearer tokens.
  • UUID Idempotency Generation: Client attaches unique idempotency key before dispatch.
  • Dual-Theme Signals: Zero-reflow dark and light mode reactive switching.

2. Application Core (Spring Boot)

Atomic Logic
  • Security Boundary: JJWT 0.12.6 + BCrypt salted credential hashing + brute-force lockout.
  • Strict Isolation: @Transactional(isolation = READ_COMMITTED).
  • Invariant Verification: Validates source balance, destination existence, and non-self transfer.
  • Streaming Engine: RFC 4180 CSV statements streamed directly to HTTP buffer.

3. Ledger Tier (Flyway Relational)

Immutable Audit
  • transfers: High-level intent, idempotency key index, and status.
  • transaction_entries: Paired DEBIT and CREDIT rows with post-balance snapshots.
  • B-Tree Indexing: Composite indexes on (account_id, transaction_reference).
  • Zero Drift: Relational FK cascading and unique constraints.

Step 3: Design Experiments 🧪

Experimental Design & Benchmark Framework

Workload synthesis, concurrent stress generation, and rigorous evaluation metrics

Workload & Chaos Synthesis

Benchmark Setup
  • Synthetic Financial Dataset: 100,000 monetary transfers distributed over 2,000 customer accounts with realistic Zipfian skew (simulating peak retail hours).
  • Concurrency Thread Pools: Evaluated under 10, 50, 100, 250, and 500 concurrent client threads.
  • Network Chaos Injection: Automated 15% packet drop and duplicate HTTP request retry harness to stress test idempotency.
  • Controlled Environment: Java 21 OpenJDK, JVM Xms2G/Xmx4G, NVMe SSD storage.

Quantitative Evaluation Metrics

Success Criteria
  • Throughput (TPS): Sustained financial transactions completed per second.
  • Latency Profile: P50, P95, and P99 latency distribution in milliseconds.
  • Ledger Balance Invariant: Sum of all DEBIT entries strictly equal to Sum of all CREDIT entries across the database (∑Debits == ∑Credits).
  • Duplicate Suppression Rate: Percentage of retransmitted duplicate transfers successfully identified and rejected.
  • Baseline Comparison: Evaluated directly against the conventional Naive In-Place Overwrite CRUD model.
